### 1.2 最终命名：Pipely

**命名理由**:

- **ASO搜索优化**: "Pipeline"是美国CRM用户搜索量最高的关键词之一，"Pipely"直接关联pipeline概念，在App Store搜索"CRM pipeline"、"sales pipeline"、"simple CRM"时排名靠前
- **品牌记忆度**: Pipely发音简短有力（pie-puh-lee），2音节，与"Simply"押韵，朗朗上口，一次听到就能记住。与"Salesforce"、"HubSpot"等企业级名字形成鲜明对比——那些名字听起来像"企业软件"，Pipely听起来像"简单工具"
- **功能描述性**: Pipeline是CRM最核心的视觉概念（Kanban看板），Pipely直接告诉用户"这是一个管pipeline的工具"，无需解释
- **情感共鸣**: "ly"后缀暗示"轻松、友好、简单"，与"overkill"的抱怨形成直接对立。用户看到Pipely就知道"这不是另一个Salesforce"
- **国际化适配**: Pipeline是全球通用的商业术语，Pipely在英语、德语、法语、西班牙语等语言中发音一致，无需本地化

**副标题**: Simple CRM for Small Teams

- 直接描述目标用户（Small Teams）和核心价值（Simple CRM）
- 包含"CRM"关键词提升ASO排名
- "Small Teams"精准定位，避免与大CRM竞争

### 1.3 App Store关键词策略

## 2. 痛点研究与客户需求

### 2.1 核心痛点总结

基于Reddit、Hacker News、Twitter等平台的深度调研，小团队CRM的核心痛点如下：

| 痛点编号 | 痛点描述 | 严重程度 | 出现频率 | 用户原话 |
|---------|---------|---------|---------|---------|
| P1 | 功能过剩(Overkill) — 现有CRM有100+功能但只用5-8个 | 🔴 极高 | 90%+ | "Salesforce is overkill for my 3 person team" |
| P2 | 价格过高 — 小团队为不需要的企业级功能付费$50-150/月 | 🔴 极高 | 85%+ | "people paying $50 to $150/month for enterprise features they never touch" |
| P3 | 设置复杂 — 需要专门的管理员或顾问来维护 | 🟠 高 | 70%+ | "We need a consultant just to change a workflow" |
| P4 | 移动端体验差 — 更新deal状态等简单操作在手机上很慢 | 🟠 高 | 65%+ | "mobile app is sluggish on simple tasks like updating a deal stage" |
| P5 | 学习曲线陡 — 新员工需要数天培训才能上手 | 🟠 高 | 60%+ | "HubSpot requires training for those who've never used a CRM before" |
| P6 | 定价跳跃 — 从免费/低价到专业版的价格跳升太大 | 🟡 中 | 55%+ | "The pricing jump feels steep for small teams" |
| P7 | 自动化被锁 — 基础自动化功能被锁在高价套餐 | 🟡 中 | 50%+ | "HubSpot works great until you need those essential automations" |
| P8 | 数据迁移困难 — 从一个CRM迁移到另一个代价高昂 | 🟡 中 | 45%+ | "Moving CRM itself is expensive in lost time" |

### 2.2 用户画像

**主要用户画像 #1: 小型代理公司老板**
- 年龄: 30-45岁
- 团队: 3-5人
- 行业: 营销代理、咨询公司、设计工作室
- 当前工具: Google Sheets + Gmail + 一些Zapier
- 月收入: $10k-50k
- CRM预算: $15-30/月（全团队）
- 核心需求: 联系人管理 + 可视化Pipeline + 邮件追踪

**主要用户画像 #2: 独立销售顾问**
- 年龄: 35-50岁
- 团队: 1-2人
- 行业: B2B销售咨询、教练
- 当前工具: 笔记本 + Excel + Gmail
- 月收入: $8k-25k
- CRM预算: $10-20/月
- 核心需求: 快速添加联系人 + 跟进提醒 + 简单报表

**主要用户画像 #3: 初创团队创始人**
- 年龄: 25-35岁
- 团队: 2-5人
- 行业: SaaS初创、技术公司
- 当前工具: Notion + Airtable + HubSpot免费版
- 月收入: $0-20k（早期阶段）
- CRM预算: $0-15/月
- 核心需求: 免费起步 + 团队协作 + 快速上手

### 2.3 用户真正需要的3件事

基于痛点分析，小团队CRM用户真正需要的只有3件事：

1. **Contacts（联系人）** — 一个地方存储所有客户信息，不再散落在Gmail、Excel、笔记本
2. **Pipeline（管道）** — 可视化看板追踪每个deal的状态，拖拽移动
3. **Follow-ups（跟进）** — 自动提醒什么时候该跟进谁，不再遗漏

> "they want contacts, a pipeline, and email tracking. that's it."
> — Reddit r/microsaas

| 竞品App | 评分 | 价格 | 核心问题 |
|---------|------|------|---------|
| Less Annoying CRM | 4.5 | $15/用户/月 | 无免费版，价格对小团队偏高 |

### 3.2 最具参考价值项目深度分析

#### 3.2.1 Twenty CRM (twentyhq/twenty)

**核心架构**:
- 前端: React + Jotai (状态管理) + Linaria (CSS-in-JS) + Lingui (国际化)
- 后端: NestJS + BullMQ (任务队列) + PostgreSQL + Redis
- 构建工具: Nx (Monorepo管理)
- 特色: 支持代码定义对象和视图，版本控制CRM配置

**可借鉴的核心设计**:
```
1. 对象定义系统 (defineObject) — 允许用户自定义数据模型
2. 视图系统 — 支持多种视图模式（表格、看板、日历）
3. 工作流引擎 — 基于触发器的自动化
4. AI Agent集成 — CRM + AI助手
5. 版本控制 — CRM配置像代码一样管理
```

**Twenty的对象定义代码（可参考的数据建模思路）**:
```ts
import { defineObject, FieldType } from 'twenty-sdk/define';

export default defineObject({
  nameSingular: 'deal',
  namePlural: 'deals',
  labelSingular: 'Deal',
  labelPlural: 'Deals',
  fields: [
    { name: 'name', label: 'Name', type: FieldType.TEXT },
    { name: 'amount', label: 'Amount', type: FieldType.CURRENCY },
    { name: 'closeDate', label: 'Close Date', type: FieldType.DATE_TIME },
  ],
});
```

**对Pipely的启示**: Twenty的"代码定义对象"理念太技术化，不适合小团队。但它的看板视图设计、拖拽交互、数据模型设计值得参考。Pipely应该用SwiftData的@Model宏来定义数据模型，更简洁直观。

#### 3.2.2 Frappe CRM (frappe/crm)

**核心架构**:
- 前端: Vue.js + Frappe UI
- 后端: Python + Frappe Framework
- 数据库: MariaDB
- 特色: 无限用户、Kanban看板、一体化Lead/Deal页面

**可借鉴的核心设计**:
```
1. All-in-One Lead/Deal页面 — 所有操作集中在一个页面
2. Kanban拖拽 — 直观的pipeline管理
3. 自定义视图 — 用户可创建个人化视图
4. Twilio/WhatsApp集成 — 通讯能力
5. 无限用户策略 — 不按用户数收费
```

**对Pipely的启示**: Frappe的"All-in-One页面"设计理念非常适合移动端——小团队用户最讨厌切换页面。Kanban拖拽是必须实现的核心交互。不按用户数收费的策略也值得Pipely采用。

#### 3.2.3 Simple-CRM (MarcoLenschau/Simple-CRM)

**核心架构**:
- 前端: Angular + TypeScript + Sass
- 后端: Firebase (Firestore + Auth)
- 特色: 极简设计，面向自由职业者

**可借鉴的核心设计**:
```
1. Firebase实时同步 — 无需自建后端
2. 响应式设计 — 适配多种设备
3. 客户记录管理 — 简单的CRUD
4. 任务追踪 — 基础的任务管理
```

**对Pipely的启示**: Simple-CRM验证了"极简CRM"的市场需求，但它的技术栈（Angular + Firebase）不适合iOS原生开发。Pipely用SwiftData + CloudKit替代Firebase，实现更原生的体验。

### 3.3 iOS原生开发参考

由于GitHub上没有高质量的Swift/SwiftUI CRM开源项目，Pipely需要从零构建iOS原生应用。但可以参考以下SwiftUI设计模式：

| 参考方向 | 推荐资源 | 用途 |
|---------|---------|------|
| Kanban拖拽 | SwiftUI DragGesture + LazyVGrid | Pipeline看板核心交互 |
| 数据持久化 | SwiftData (iOS 17+) | 本地数据存储 |
| 云同步 | CloudKit (免费) | 跨设备同步 |
| 邮件集成 | MessageKit / Gmail API | 邮件追踪 |
| 通知系统 | UserNotifications + Live Activities | 跟进提醒 |

### 3.4 二次开发策略

**结论**: 不直接fork任何开源项目，而是参考其设计理念和架构模式，从零构建iOS原生应用。

**理由**:
1. 所有高质量CRM开源项目都是Web技术栈（React/Vue/Angular），无法直接用于iOS
2. iOS原生体验是Pipely的核心竞争优势之一（解决P4移动端体验差）
3. SwiftData + CloudKit提供零成本后端，无需维护服务器
4. 参考Twenty的数据模型设计、Frappe的UI交互模式、Simple-CRM的极简理念

import UserNotifications
import SwiftUI

final class NotificationService: NSObject, UNUserNotificationCenterDelegate {
    static let shared = NotificationService()
    
    private override init() {
        super.init()
        UNUserNotificationCenter.current().delegate = self
    }
    
    func requestAuthorization() async -> Bool {
        do {
            return try await UNUserNotificationCenter.current()
                .requestAuthorization(options: [.alert, .badge, .sound])
        } catch {
            return false
        }
    }
    
    func scheduleFollowUpReminder(_ followUp: FollowUp) async {
        guard let reminderDate = followUp.reminderDate else { return }
        guard reminderDate > Date() else { return }
        
        let content = UNMutableNotificationContent()
        content.title = "Follow-up Reminder"
        content.body = "\(followUp.type.iconName) \(followUp.contact?.fullName ?? "Contact")"
        if !followUp.notes.isEmpty {
            content.body += " — \(followUp.notes)"
        }
        content.sound = .default
        content.categoryIdentifier = "FOLLOW_UP"
        content.userInfo = ["followUpId": followUp.id.uuidString]
        
        let trigger = UNCalendarNotificationTrigger(
            dateMatching: Calendar.current.dateComponents(
                [.year, .month, .day, .hour, .minute],
                from: reminderDate
            ),
            repeats: false
        )
        
        let request = UNNotificationRequest(
            identifier: followUp.id.uuidString,
            content: content,
            trigger: trigger
        )
        
        try? await UNUserNotificationCenter.current().add(request)
    }
    
    func cancelReminder(_ followUp: FollowUp) {
        UNUserNotificationCenter.current()
            .removePendingNotificationRequests(withIdentifiers: [followUp.id.uuidString])
    }
    
    func userNotificationCenter(
        _ center: UNUserNotificationCenter,
        didReceive response: UNNotificationResponse,
        withCompletionHandler completionHandler: @escaping () -> Void
    ) {
        let userInfo = response.notification.request.content.userInfo
        if let followUpIdString = userInfo["followUpId"] as? String,
           let followUpId = UUID(uuidString: followUpIdString) {
            NotificationCenter.default.post(
                name: .followUpTapped,
                object: nil,
                userInfo: ["followUpId": followUpId]
            )
        }
        completionHandler()
    }
}

import StoreKit

@Observable
final class StoreKitService {
    var isProUser = false
    var subscription: Product.SubscriptionInfo.Status?
    var monthlyProduct: Product?
    var yearlyProduct: Product?
    
    private var updateTask: Task<Void, Never>?
    
    static let productIDMonthly = "com.pipely.crm.pro.monthly"
    static let productIDYearly = "com.pipely.crm.pro.yearly"
    
    func loadProducts() async {
        do {
            let storeProducts = try await Product.products(for: [
                Self.productIDMonthly, Self.productIDYearly
            ])
            monthlyProduct = storeProducts.first { $0.id == Self.productIDMonthly }
            yearlyProduct = storeProducts.first { $0.id == Self.productIDYearly }
        } catch {
            return
        }
        
        updateTask = listenForTransactions()
        
        if let monthly = monthlyProduct,
           let status = try? await monthly.subscription?.status.first {
            updateSubscriptionStatus(status)
        }
    }
    
    func purchase(_ product: Product) async -> Bool {
        do {
            let result = try await product.purchase()
            switch result {
            case .success(let verification):
                if case .verified(let transaction) = verification {
                    await transaction.finish()
                    isProUser = true
                    return true
                }
            default:
                break
            }
        } catch {
            return false
        }
        return false
    }
    
    private func listenForTransactions() -> Task<Void, Never> {
        Task.detached { [weak self] in
            for await result in Transaction.updates {
                if case .verified(let transaction) = result {
                    await transaction.finish()
                    await MainActor.run {
                        self?.isProUser = transaction.expirationDate?.compare(Date()) == .orderedDescending
                            || transaction.expirationDate == nil
                    }
                }
            }
        }
    }
    
    private func updateSubscriptionStatus(_ status: Product.SubscriptionInfo.Status) {
        switch status.state {
        case .subscribed, .inGracePeriod, .inBillingRetryPeriod:
            isProUser = true
        default:
            isProUser = false
        }
        subscription = status
    }
}

### 5.10 编写规则

| 规则 | 说明 |
|------|------|
| 架构模式 | MVVM + SwiftData，View只负责UI，ViewModel处理业务逻辑 |
| 状态管理 | 使用@Observable + @Query，避免Combine复杂性 |
| 导航 | NavigationStack + NavigationLink，使用.sheet和.fullScreenCover |
| 数据持久化 | SwiftData (iOS 17+)，自动CloudKit同步 |
| 错误处理 | 使用async/await + Result类型，避免try?隐藏错误 |
| 命名规范 | View后缀View，ViewModel后缀ViewModel，Service后缀Service |
| 代码组织 | 每个功能模块一个文件夹，Models/Views/ViewModels/Services分层 |
| 无注释原则 | 代码即文档，函数名和变量名必须自解释 |
| 主题系统 | 使用Color+Theme扩展统一管理颜色，支持深色模式 |
| 国际化 | 所有用户可见字符串使用String(localized:) |

### 9.2 Pipely定价策略：站内订阅B

**选择理由**: Pipely属于"功能稍微复杂"类别——需要CloudKit同步、通知服务、邮件集成等，有持续的服务成本（虽然CloudKit免费额度很大），因此采用站内订阅B模式。

**核心定价原则**:
1. **免费版必须有足够价值** — 让用户真正用起来，不是demo
2. **付费版价格必须远低于竞品** — 小团队对价格极度敏感
3. **不按用户数收费** — 这是小团队最大的痛点之一
4. **年付折扣要足够大** — 提高LTV，降低流失

### 9.6 免费版限制的心理学设计

| 限制 | 免费版 | Pro版 | 为什么这样设限 |
|------|--------|-------|--------------|
| 联系人 | 50个 | 无限 | 50个够用1-2个月，之后自然增长触发升级 |
| Deals | 20个活跃 | 无限 | 20个活跃deal是小团队的临界点 |
| 跟进提醒 | 每日3个 | 无限 | 3个提醒让用户尝到甜头，但不够用 |
| 团队 | 1人 | 5人 | 单人免费，团队协作是付费价值 |
| Pipeline | 1个 | 无限 | 大多数小团队1个pipeline够用，多pipeline是进阶需求 |
| 导出 | ❌ | CSV | 导出是"安全感"需求，付费用户最在意 |

**假设**: 7%免费到付费转化率（行业平均3-5%，Pipely因价格低预期更高），月流失率5%。

### 9.8 定价策略总结

Pipely的定价核心是**"不按用户数收费 + 远低于竞品"**。这个策略直接解决了P1（功能过剩）和P2（价格过高）两个最核心的痛点。$9.99/月全团队的价格，让小团队从"负担不起"变成"为什么不试试"。

## 附录：关键决策记录

| 决策 | 选择 | 理由 |
